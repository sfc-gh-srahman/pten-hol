ML lifecycle

One governed path from tag data to a live risk score

Here is the same story as a path you will walk in the next forty minutes. Raw tag values become stand-level features in the Feature Store. Live scoring · ScoreRigNow

The agent scores live through a procedure, not by calling the container

The procedure is the tool; the service is the model behind it. The warm service answers in about 3 s per call vs about 12 s for a cold warehouse function.

This is how live ML reaches the agent. When someone asks to score a rig now, DSA_AGENT picks the custom tool ScoreRigNow, backed by SCORE_RIG_NOW, a SQL stored procedure running on the HOL_PTEN_WH warehouse. The procedure reads the latest 1 to 20 stands for that rig from the Feature Store view STAND_DRILLING_FEATURES$V1, then calls HOL_PTEN_ML.ML.STUCK_PIPE_SVC!PREDICT_PROBA. That is the inference service on Snowpark Container Services, running on the HOL_PTEN_POOL compute pool and serving STUCK_PIPE_MODEL version V1 from the Model Registry. The risk per stand comes back as JSON to the agent, which writes the answer. The key point: the agent never calls the container directly. The procedure is the tool and the service is the model behind it. Because the service stays warm, a call takes about 3 seconds instead of about 12 seconds for a cold warehouse function. Below it, GetTagWindow (GET_TAG_WINDOW) is the sibling custom tool: plain SQL retrieval of raw 1-minute tags, no model involved.

Architecture · custom RAG

Custom RAG means running every component yourself, with data copied out

Each box is a separate system to secure, refresh and pay for, with governance set per system.

Start with the generic pattern so the trade-offs are concrete. The app sends a question to an orchestrator you write and operate. It calls an external embedding API, queries a vector database you manage and keep refreshed, then calls a hosted LLM API with the retrieved context. The documents have to be copied out to feed the index. None of this is wrong, but every box is its own system with its own credentials, refresh job and access model.
Architecture · LangChain on Snowflake

LangChain on Snowflake keeps your chain in code while the data stays in Snowflake

You still own the chain: prompts, retries and version pins. Retrieval, generation and data stay inside the account.

Same pattern, but every service the chain calls is in Snowflake. The notebook is the orchestrator. The langchain-snowflake retriever queries the Cortex Search service, which handles embeddings and hybrid search, and ChatSnowflake calls a Cortex LLM. The parsed chunks never leave Snowflake. What the team still owns is the chain itself: the prompt, retries, package versions and any tracing, which is why we add TruLens next.

One agent, three kinds of tools

Observability · custom RAG

Custom RAG observability is a second stack you bring and run

Traces and scores live outside the governed data, in tools you select, connect and maintain.

With a custom build, observability is not there until you add it. You instrument the orchestrator, send logs to a separate store, and run an external evaluation harness for answer quality. It works, but it is another set of systems to operate and govern, and the traces sit outside the platform holding the data.
Observability · LangChain + TruLens

TruLens on Snowflake records the chain and its scores inside the account

Observability exists because you added TruLens, but the traces and scores land in Snowflake.
